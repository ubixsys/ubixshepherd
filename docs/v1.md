# Version 1: the Fold and dispatch, aimed at uBixCore

**Status:** Scope and stack decided by the maintainer on 2026-10-01. Everything below the
"Decided" section is a proposal for how to build it, open to argument.

## Decided

| Call | Decision |
|---|---|
| What v1 delivers | **The Fold and dispatch together**: lanes, leases, reservations and worktrees as a service, plus Shepherd starting agents from work orders and routing each one to a provider and model. |
| Where it runs | **Over a workspace, not a repo.** One daemon per machine; the workspace is a directory of repos (`~/git`), and the front desk runs at its root so work spans projects (see [design.md §3.14](design.md#314-workspaces-one-shepherd-over-many-repos)). |
| Where it is proven | **`ubixcore`** first, then a host product built on it (whose sessions already do much of their work in ubixcore), then a repo that is not uBixCore. |
| Stack | **Go core, TypeScript web UI.** One Go binary per OS (Windows, macOS, Linux) holds the daemon, the `shepherd` CLI, the MCP server and the HTTP API. The web UI comes later and is written in TypeScript/React, so it can reuse `@ubixsys/ubixcore`. |
| Where the human talks to it | **The terminal first.** A web page later. |
| Audience | **Anyone's repos; aimed at uBixCore.** The core knows nothing about uBixCore; a uBixCore **pack** gives uBixCore repos the deepest integration, and generic packs serve everyone else (see [design.md §3.12](design.md#312-packs-useful-to-anyone-best-with-ubixcore)). |
| Forges | **GitLab and GitHub, both in v1.** GitLab as the primary forge (MRs, CI, sign-off); GitHub at least as the release mirror, where tags trigger the workflows that publish images (see [design.md §3.13](design.md#313-forges-primary-and-mirror)). |
| Enterprise | **Future, not MVP.** A hosted, login-protected Shepherd at `shepherd.ubixsys.com`. v1 only keeps that door open (see [Keeping the hosted path open](#keeping-the-hosted-path-open)). |

## Why the Fold first, from the numbers

uBixCore's `AGENTS-COORD.md` on 2026-10-01 (see [origins.md](origins.md#scale-today)):
20 registered lanes, 307 log entries in 541 lines, 32 git worktrees, two tag races in two
days (v0.39/v0.40, v0.43/v0.44), and lessons for "the next lane" written as paragraphs in
the log. The protocol is right; the medium has run out. Dispatch comes in the same version
because the point is a larger swarm, and a swarm Shepherd cannot start is still one the
human starts by hand.

## Shape

```
              you (terminal)
                    │
        front desk: any MCP-capable agent session,
        wired to Shepherd's operator tools
                    │ MCP
 ┌──────────────────┴──────────────────────────────┐
 │ shepherd (Go, one binary)                        │
 │  daemon ─ HTTP API ─ MCP server ─ CLI            │
 │  Fold: lanes · leases · reservations · worktrees │
 │  Dispatch: work orders · routing · adapters      │
 │  Proofs: forge sync · gate runner                │
 │  Store: SQLite (local)                           │
 └───┬──────────────┬──────────────┬───────────────┘
     │ starts       │ MCP (worker) │ API
  agents in      agents report  git pre-push hook,
  worktrees      and ask        GitLab + GitHub (polled in v1)
```

- **The daemon owns all state.** The CLI, the MCP server and (later) the web UI are clients
  of one HTTP API. Nothing else touches the store.
- **The front desk can live in any MCP client**: a Claude Code session in the terminal,
  or VS Code's agent mode or the Claude Code extension in VS Code. It runs at the
  **workspace root** (`~/git`), not inside one repo.
- **The front desk is a client, not the shepherd.** Your single thread is an ordinary agent
  session given Shepherd's *operator* tools. It drafts work orders and summarises; the
  daemon decides, routes and verifies. "The shepherd is not a sheep" holds: swap the front
  desk for the CLI and nothing changes but the typing.
- **Two tool sets.** *Operator* tools (create work order, status, answer a held decision,
  close a lane) are for the human's session. *Worker* tools (report progress, ask a
  reserved question, request a lease) are for dispatched agents. The split becomes the role
  model when logins arrive.

## The Fold in v1

| Today in `AGENTS-COORD.md` | In Shepherd |
|---|---|
| Add a row to §1, pick a distinct prefix, run `git worktree add` by hand (`code:worktree` was never ported) | `shepherd lane open <name> --scope '<globs>'` creates the branch off fresh `origin/main` (or the repo's base), the worktree, and the lane, in one step. Prefix uniqueness is checked, not remembered. |
| Claim shared paths in the §6 log | Shared paths come from the repo's pack, overridable per repo (for ubixcore, from the uBixCore pack: root `README.md`, `CLAUDE.md`, `php/Ubix/*`, `js/Ubix/*` / `ts/Ubix/*`, `app/<App>/src/{Routes,Dependencies}.php`, `.gitlab-ci.yml`, `composer.lock`). A lane's scope that touches one takes a **lease**; an overlapping scope is refused or queued at `lane open`, before any work starts. |
| Honour system | A **pre-push hook** (`.githooks/`, which ubixcore already has) asks Shepherd whether the pushed diff stays inside the lane's scope and leases, and refuses otherwise. |
| "Tagged v0.40.0 (v0.39.0 went to db-test-case)" | `shepherd tag reserve <repo> minor` hands out the next version atomically against remote tags *and* live reservations. At close, Shepherd checks the tag points at a commit that contains the merge (the v0.29/v0.30 trap). |
| "LANDED !205 at a7b522c5, claims released", typed by the agent | Leases and reservations are released by the merge Shepherd sees itself. |
| 32 worktrees, some long dead | `lane close` removes the worktree after the merge is proven; `shepherd fold gc` lists worktrees whose branch is merged or gone. |
| "Worth knowing for the next lane: …" in a log paragraph | `shepherd note` records a lesson as a typed record against the repo and paths. v1 shows notes to agents whose scope touches those paths; promoting them into the standards pack or a gate is phase 5. |

**Cutover.** `shepherd fold import` reads the lane table and `git worktree list` into
lanes; the old log is archived, not parsed. During the cutover Shepherd renders
`AGENTS-COORD.md` as a generated read-only view, so a session not yet on Shepherd still
sees who holds what. ubixcore's `CLAUDE.md` coordination section changes to "use
`shepherd`" in the same MR that turns the hook on.

## Dispatch in v1

1. **Work order.** Plain patterns (`review !205`, `release ubixcore minor`) become work
   orders by rule. Anything else is drafted by the front desk, or, from an entry point with
   no model in front (`shepherd do "…"`), by a **triage** task routed like any other kind to
   the person's cheapest allowed service ([design.md §3.11](design.md#311-routing-the-right-agent-for-the-work)).
   The work order
   ([design.md §3.3](design.md#33-typed-work-orders)) has a `kind` (`code-change`,
   `review`, `docs`, `research`, …). The daemon validates it against the JSON Schema and
   shows it back; nothing runs on an invalid order.
2. **Routing.** A rules table picks provider and model
   ([design.md §3.11](design.md#311-routing-the-right-agent-for-the-work)).
3. **Lane and start.** Shepherd opens the lane (scope from the order), then starts the
   agent in that worktree through a provider **adapter**: v1 ships adapters for Claude Code,
   Copilot, Cursor and OpenCode in their non-interactive modes. Each adapter turns the work order into
   that provider's prompt. A concurrency limit per machine is a setting.
4. **Proof, not claims.** When the agent reports done, **Shepherd runs the repo's gate
   itself** in the worktree at the reported commit; `gate-green` is recorded only if it
   passes on the branch head. MR and merge states come from GitLab.
5. **Held decisions.** An agent that hits a reserved class (pricing, published copy,
   destructive production, …) calls `ask`; the task moves to `blocked: decision` and the
   question lands in your thread with options and a recommendation. Path rules from the
   repo config also hold a task without the agent's help.
6. **Outcome record.** Every task records provider, model, kind, gate result on first try,
   rework count, wall time, and tokens/cost when the provider reports them. This is the
   evidence routing changes are made from.

Credentials in v1 are the provider CLIs' own logins on the machine running Shepherd.
Leasing scoped credentials from uBixVault is phase 4 of the design and stays there.

## Forges in v1: GitLab primary, GitHub mirror, polled

Every forge sits behind one interface. v1 ships two implementations:

- **GitLab, primary:** MRs, pipelines, approvals, merge SHAs, tags.
- **GitHub, mirror role:** the release path for repos that mirror to GitHub (ubixcore,
  ubixvault, replikate today). Shepherd checks that the mirror carries the merge and the
  tag, that the tag-triggered workflow ran and succeeded (and starts it with
  `workflow_dispatch` when the tag arrived without triggering it, a failure seen on
  2026-10-01), and that the published artefact exists, for example an anonymous pull of the
  `ghcr.io` image. That gives the state machine a **`published`** state with proof.

GitHub as a *primary* forge (pull requests, reviews, branch protection as the sign-off) is
the same interface with more of it implemented, and comes straight after the MVP.

A Shepherd on a laptop cannot receive webhooks. v1 therefore **polls** both forges for the
MRs, pipelines and workflow runs of open lanes (cheap: only those). When Shepherd runs somewhere
reachable (the k3s cluster, or the hosted service), uBixOps forwards its webhooks instead
and polling becomes the fallback. Same state machine either way. A forge host that cannot be reached
(a network failure or a 5xx, not a refusal such as a 401 or 404) is skipped for a wait that
doubles from a minute to 15 and resets on its first answer, so a laptop offline does not
fail every lane on every poll; the daemon logs once when the host goes down and once when
it is back.

The pre-push hook is the only lease enforcement in v1. A CI check needs a Shepherd the CI
runner can reach, so it arrives with the server-side deployment.

## Keeping the hosted path open

Cheap now, expensive to retrofit:

- **Every client goes through the HTTP API**, including the CLI on the same machine.
- **Everything is scoped to a workspace**, which becomes a team or organisation when hosted.
- **Authentication is pluggable**: none or a local token for a single user on localhost;
  real logins (and the operator/worker role split) when hosted.
- **The store sits behind an interface.** SQLite (a pure-Go driver, so cross-compiling
  stays trivial) locally; MariaDB or Postgres when hosted.
- **Repos, packs, forges and providers are configuration**, not code. Nothing in the core
  knows it is ubixcore except the pack that says so, and a CI check in this repo fails if
  core code names a product (the same boundary check uBixCore runs on itself).

## Out of v1

The standards pack renderer and drift check (design phase 1, now next after v1), the web
UI, the hosted service and logins, Discord, Vault credential leasing, playbooks, and
promoting notes into rules (the learning loop). Routing outcomes are **recorded** in v1;
changing routing from them is by hand.
